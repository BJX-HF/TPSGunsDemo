## 0. 三句话结论

1. **不是分段式。** 现状是「**每发脉冲累加 → 停火延迟 → 一次回正**」的单段模型；文档要的是「**上抬 → 瞬时回弹 → 稳定 → 下降**」四段式时间轴。
2. **不支持四段曲线。** 现状只有两条曲线能影响单发轨迹：`VerticalKickCurve`（**按发序号**缩放幅度）与 `RecoveryCurve`（**按归一化回正时间**整形进度）。文档要的「上抬曲线 / 下降曲线」这类**按阶段内时间**整形形状的曲线，本项目没有。
3. **"分段"这个词在两套体系里指的是不同的东西** —— 现状的分段在**发数轴**上（第几发），文档的分段在**时间轴**上（这一发的第几毫秒）。这是本次误解的根源。

## 1. 逐条对照

| 维度 | 参考文档 §2 | 本项目现状 | 差距 |
| --- | --- | --- | --- |
| 单发模型 | 四段：t0 上抬 / t1 瞬时回弹 / t2 稳定 / t3 下降 | 单段：一发一个脉冲，随后停火回正 | **模型不同** |
| 阶段时长 | 各阶段独立可配（`阶段时长`） | 只有 `RecoveryDelay` + `RecoveryTime` 两个 | 缺 2 个可调维度 |
| 形状整形曲线 | 上抬曲线、下降曲线、连射回正曲线（`插值曲线`） | `VerticalKickCurve`（发序号轴）、`RecoveryCurve`（时间轴，但只作用于"下降"那一段） | 缺"上抬"与"回弹"两段的曲线 |
| 瞬时回弹 | 独立阶段，特征是**在稳定前回弹到一个比例** | **无**。累加只会继续加，不会回弹 | 缺整个阶段 |
| 应用方式 | 目标值 → **帧间增量**，每帧推相对量 | **直接写累加值**（`AccumulatedPitch/Yaw`），相机每帧读绝对值 | 表述等价，**不是**缺失（见 §3.1） |
| 时间跨界处理 | 显式把累计时间钳到阶段终点，保证曲线跑满 100% | 无阶段概念，故无跨界问题 | 随模型引入 |
| 连射回正分段 | 「按连续射击次数配置最大回正时间」 | **有** —— `RecoveryTime` 是常数，但 `VerticalKickCurve` 按发序号放大幅度，等效于"越打越难压" | **部分已有**，但不是回正时间维度 |
| 回正忽略阈值 | 「小于阈值的移动可不触发持续回正」 | **无** —— 只要有残留就一定会走完回正 | 缺一个死区 |
| 中段稳定 | t2 稳定段（Plateau），期间目标值不变 | **有隐含对应** —— `RecoveryDelay` 期间偏移冻结不动 | 已覆盖 |
| Roll | 衰减包络 × 周期震动 | 已实现（P8） | **无差距** |

## 2. 现状的真实轨迹（用当前数值画出来）

以 `DA_Recoil_Rifle_S` 为例，站姿、`Scale = 1.0`、`TimeBetweenShots = 0.12s` 连发 3 发后停火。
参数：`RecoveryDelay = 0.12`、`RecoveryTime = 0.30`、`RecoilReturnRatio = 0.15`、`RecoveryCurve` = 线性。

```
Pitch(°)
   ^
   |
0.47|            ●第二发打完(0.318+0.151)
   |           /|
0.32|     ●第一发打完       ╲
   |    /|  (0.190)          ╲__ τ 起点=0.468
0.19|   / |                     ╲
   |  /  |                       ╲
0.085| ●   |                        ╲
   |/|   |                          ╲
  0├─┼───┼────────────────────────────╲──────────► 时间
    0.12 0.24                      0.24+0.30=0.54
    │← Delay 冻结 →│←────── 一次线性回正 ──────→│
                                                    ▼
                                              停在 0.468×0.15 = 0.070°
```

三个特征：

1. **上升是"阶梯"不是"斜坡"**。每次开火在 `ApplyShot()` 内**瞬时**加一个 Kick，两发之间完全平坦。没有"上抬用了多久"这个概念 —— 上抬是 0 秒。
2. **回弹段不存在**。打完最后一发，偏移**停在峰值**（`Accumulating`，偏移冻结）等 `RecoveryDelay` 过完，然后**一次性开始**单调下降。
3. **回正结束后有残留**，残留 = 峰值 × `RecoilReturnRatio`。这是刻意设计（P2 §5.2 拍板过）。

## 3. 关键判断：这算不算"没有分段"？

**是，但这不等于现有实现是错的。** 讲清三点，避免来回改。

### 3.1 「目标值 → 帧间增量」不是缺失，是等价表达

文档强调这一点，是因为它要**把极短阶段画成曲线** —— 曲线需要一个"进度 t ∈ [0,1]"来取值，
所以必须先算出"当前时刻的目标值"再取差分。

现状直接把积累结果写进 `AccumulatedPitch`，相机每帧读绝对值。两者**在数学上是同一个东西**：
`AccumulatedPitch = Σ 目标增量`。所以这条**不是问题**，不需要改。

真正缺的是**"目标值"本身没有形状** —— 现状的目标值是阶跃（0 → Kick），文档的目标值是曲线（上抬曲线采样）。

### 3.2 现状用「发序号轴曲线」替代了「时间轴曲线」

`VerticalKickCurve` 的横轴是 **ShotIndex**，不是时间。用它可以做出"前几发轻、后几发重"，
所以**观感上已经有一点"分段"** —— 只不过分段依据是**打了多少发**，而不是**这一发过了多久**。

这正是两套体系最容易混淆的地方：

| | 横轴 | 回答的问题 | 本项目 |
| --- | --- | --- | --- |
| `VerticalKickCurve` | 发序号 | "第 8 发该比第 1 发重多少？" | ✅ 有 |
| `RecoveryCurve` | 归一化回正时间 | "回正该快回还是慢回？" | ✅ 有 |
| 上抬曲线（文档 t0） | **阶段内**归一化时间 | "这 0.03 秒里是匀速抬还是加速度抬？" | ❌ 无 |
| 下降曲线（文档 t3） | 阶段内归一化时间 | "这 0.15 秒里是慢降还是陡降？" | ⚠️ 被 `RecoveryCurve` 部分覆盖（见下） |

**`RecoveryCurve` 其实已经是"下降曲线"了** —— 它整形的是回正过程。差别在于文档把它拆成
「回弹后进入稳定，再下降到目标」而现状是「延迟后直接下降到目标」。**中间少了一次回弹。**

### 3.3 手感上的实际差别（这是唯一真正能感知到的）

| 场景 | 文档四段式 | 本项目现状 | 玩家感知 |
| --- | --- | --- | --- |
| 单点一枪 | 抬起来 → **立刻往回弹一点** → 稳住 → 慢慢降 | 抬起来 → 稳住 → 慢慢降 | 四段式有"**一顿**"的顿挫感，现状是"抬一下再滑回来" |
| 连发中段 | 每发都走完 t0~t3 的压缩版本 | 每发只加一个脉冲，累积成斜坡 | 差异不明显 |
| 极短阶段 | 有跨界钳制，曲线一定能跑满 | 无此概念 | 配置 0.06s 这种极短阶段时，四段式更可控 |

**一句话：四段式买的是"单发的顿挫感"，现状买的是"连发的弹道形状"。** 两者不冲突，但侧重不同。

## 4. 若要落地四段式：改什么、代价多大

> 本节只是估算，未动代码。

### 4.1 数据层（`ULyraRecoilProfile`）

需新增：

| 参数 | 用途 | 默认值建议 |
| --- | --- | --- |
| `bUseStagedRecoil` | 模型开关。`false` = 走现状（向后兼容）；`true` = 走四段式 | `false` |
| `StageDuration_Lift` | t0 上抬时长 | `0.03` |
| `StageDuration_Rebound` | t1 瞬时回弹时长 | `0.02` |
| `StageDuration_Settle` | t2 稳定时长 | `0.02` |
| `StageDuration_Drop` | t3 下降时长 | `0.18` |
| `ReboundRatio` | t1 回弹到峰值的比例 | `0.55` |
| `LiftCurve` / `DropCurve` / `ReboundCurve` | 三段各自的形状曲线 | 线性 |
| `RecoveryIgnoreThreshold` | 回正忽略阈值（文档 §2.2） | `0.02` 度 |

### 4.2 运行时（`FRecoilRuntimeState`）

- 新增阶段枚举 `ERecoilStage { Lift, Rebound, Settle, Drop }` 与阶段内计时器。
- `Advance()` 内加**跨界钳制**（文档 §2 明确要求）：`预计时间 > 阶段终点` 时把时间钳到终点。
- 新增"每帧目标值 → 差分 → 增量"的通路，替代现在的"直接累加"。
- **与 Roll 的关系**：完全正交，Roll 不受影响（它自己一套时钟）。

### 4.3 波及面（这才是真正的代价）

| 受影响项 | 影响 | 处理 |
| --- | --- | --- |
| **Golden 数据（3 份 JSON）** | `RecoilGolden_*.json` 记录逐发 Kick 与累计，四段式下**逐帧轨迹变了**，逐发累计的中间态会不同 | 必须重导（`gen-recoil-golden.ps1`） |
| **自动化测试** | `Lyra.Recoil.State.*` 5 个 + `Lyra.Recoil.Pattern.Golden` 依赖现模型语义 | 需逐个复核，估计 4~6 个要改断言 |
| **CSV 列契约** | `TimeSinceFire` / `RecoveryProgress` 的语义会变（阶段内 vs 全程） | 契约测试要同步 |
| **中段稳定段的实现位置** | 现状靠 `RecoveryDelay`，四段式靠 `StageDuration_Settle` —— **两个参数语义重叠** | 需明确：四段式下 `RecoveryDelay` 是否废弃 |
| **两把枪的配方（07 文档）** | 所有手算逐发表都要重算 | 重跑手算脚本 |
| **回正忽略阈值** | 新增死区会改变"何时判定回正完成"，可能影响 `RefireDuringRecovery` 用例 | 需专门测试 |

**估算：这是一次 P2 级别的重构，不是增量补丁。** 核心风险不在写代码，而在**现有 24 个测试与 3 份 Golden 全部要重新建立基线** —— 且旧基线一旦丢失，"有没有改坏 Pitch/Yaw"这个判据也就没了。

## 5. 我的建议（供拍板）

> **✅ 已拍板并落地：走路 1。**
> 实际实现与本文建议的差异（记录备查）：
> - 开关名不叫 `bUseStagedRecoil`，而是枚举 `ERecoilSingleShotMode { InstantWrite, Interpolated }`（更明确、可扩展）。
> - 参数不是"约 8 个"而是 **6 个**：`SingleShotMode` / `LiftDuration` / `ReboundDuration` / `ReboundRatio` / `LiftCurve` / `ReboundCurve`。
> - **`Settle` 段直接复用 `RecoveryDelay`，没有引入 `StageDuration_Settle`** —— 消除了本文 §4.3 里担心的"两个参数语义重叠"问题。
> - Golden 与老测试**确认零改动**：靠"逻辑偏移 / 补间输出"双字段设计实现（见 10 号文档 §2）。

**三条路，按推荐度排序：**

### 路 1（推荐 → **已采纳**）：保留现状作为默认，四段式作为**可选高阶模型**

- 加 `bUseStagedRecoil` 开关，**默认 `false`**。
- 现有资产、Golden、24 个测试**全部不动**，零回归风险。
- 想要顿挫感的枪单独开开关、单独导 Golden。
- 代价：资产上多一组（约 8 个）参数，理解成本略增。

### 路 2：先做一个"回弹"最小增量

不动整个时间轴模型，只在**打完最后一发、进入 `Accumulating` 时**插一个瞬时回弹：
偏移先掉 `ReboundRatio`，再等 `RecoveryDelay`，再走回正。

- 只加 1 个参数（`ReboundRatio`），改动量 ≈ 20 行。
- 能拿到四段式**大部分的可感知收益**（那一"顿"）。
- 代价：仍不是严格四段式，阶段时长不可配。
- **这是性价比最高的一条。** 但如果目标是对齐文档，它不算"做完了"。

### 路 3：完整替换为四段式

严格对齐文档 §2。代价见 §4.3：**需要重建全部测试基线**，且新旧模型不可共存（除非同时走路 1 的开关）。
