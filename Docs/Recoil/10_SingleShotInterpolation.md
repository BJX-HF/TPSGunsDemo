## 0. 一句话说清这次要做什么

原来的单发后坐力是**瞬时**的：开火那一帧直接把 Kick 加到累加值上，上抬耗时 = 0。

这次给后坐配置表加一个开关，让**两套模型共存**：

| 模式 | 行为 | 用途 |
| --- | --- | --- |
| `InstantWrite` | 现状。开火瞬间把幅度写进偏移，上抬耗时 0 秒 | 连发向武器，弹道形状由「发数」堆出来 |
| `Interpolated` | 新增。单发走「上抬 → 回弹 → 下降」的时间轴，每帧推增量 | 单发向武器，买的是那一下「顿挫感」 |

**默认 `InstantWrite`**，所以既有资产、Golden 数据、自动化测试基线一个都不动。

## 1. 阶段划分（三段式）

参考文档 §2 给的是四段（`t0 上抬` / `t1 瞬时回弹` / `t2 稳定` / `t3 下降`）。

本项目落地时**合并为三段** —— 因为「稳定段」在本项目里已经有一个现成的旋钮 `RecoveryDelay`（停火后开始回正的延迟），它的语义和文档里的 t2 完全重合，没必要再引入一个意思一样的参数。

```
幅度
 ^
 |        ╱‾‾╲                     ← t1 回弹终点
 |      ╱      ╲
 |    ╱          ╲
 |  ╱              ╲
 |╱                  ╲___
 +────────────────────────╲──────────► 时间
 │←── t0 上抬 ──→│←t1→│←─ RecoveryDelay ─→│←──── t2 下降 ────→│
      (插值曲线)   回弹      稳定（复用现有参数）    (插值曲线)
```

| 段 | 参数 | 单位 | 说明 |
| --- | --- | --- | --- |
| t0 上抬 | `LiftDuration` | 秒 | 从 0 抬到**本发目标幅度** |
| t1 回弹 | `ReboundDuration` | 秒 | 从峰值回弹到 `峰值 × ReboundRatio` |
| t2 稳定 | `RecoveryDelay` | 秒 | **复用现有参数**，期间偏移冻结 |
| t3 下降 | `RecoveryTime` | 秒 | **复用现有参数**，回正到 `峰值 × RecoilReturnRatio` |

三条曲线：

| 曲线 | 横轴 | 纵轴 | 缺省行为 |
| --- | --- | --- | --- |
| `LiftCurve` | t0 段归一化进度 [0,1] | 上抬完成度 [0,1] | 无数据时退化为线性 |
| `ReboundCurve` | t1 段归一化进度 [0,1] | 回弹完成度 [0,1] | 无数据时退化为线性 |
| `RecoveryCurve` | t3 段归一化进度 [0,1] | 回正进度 [0,1] | **现有曲线，继续复用** |

> **给策划的一句话**：`Duration` 决定「这一段花多久」，`Curve` 决定「这一段的形状是匀速还是变速」。

## 2. 两条链路与两套偏移（关键设计）

这是本方案**回归风险最小**的核心原因，必须先讲清。

### 2.1 问题

`AccumulatedPitch/Yaw` 现在同时被三件事读：

1. **回正逻辑** —— 峰值取 `AccumulatedPitch`，回正目标 = 峰值 × `RecoilReturnRatio`
2. **弹道链** —— `GetShotDirectionOffset()` 虽然不累加，但 `ShotHistory` 记录的是 `AccumulatedPitch`
3. **CSV 导出 / Golden 数据 / 24 个自动化测试** —— 全都直接读 `AccumulatedPitch`

如果插值模式直接改写 `AccumulatedPitch`，上面三处全部要重导基线。**代价太大，而且丢了「有没有改坏」的判据。**

### 2.2 解法：逻辑偏移 + 补间输出

新增一个**只在 `Interpolated` 模式下生效**的输出通道：

| 字段 | 含义 | 谁写 | 谁读 |
| --- | --- | --- | --- |
| `AccumulatedPitch` / `AccumulatedYaw` | **逻辑偏移**：这一发「应该」抬到哪 | 两套模式都写 | 回正逻辑、`ShotHistory`、CSV、Golden、测试 |
| `CameraOffsetPitch` / `CameraOffsetYaw` | **补间输出**：相机「这一帧」实际看到的 | 仅 `Interpolated` 写 | 相机链 |

相机链改为读 `CameraOffsetPitch/Yaw`。在 `InstantWrite` 模式下，补间输出**恒等于**逻辑偏移 —— 所以：

- 既有 24 个测试读 `AccumulatedPitch` → **行为完全不变**
- 3 份 Golden 读 `AccumulatedPitch` → **无需重导**
- CSV 7 列契约 → **不动**

```
InstantWrite:   AccumulatedPitch ──┬──► 回正/CSV/Golden/测试
                                    └──► CameraOffsetPitch（恒等拷贝）──► 相机

Interpolated:   AccumulatedPitch ──┬──► 回正/CSV/Golden/测试
                                    └──► CameraOffsetPitch（逐帧补间）──► 相机
```

## 3. 核心算法（策划可直接对照本文调参）

### 3.1 参考文档 §2 原始伪码

```
过程 计算后座上抬():
    进度 = 当前后座时间 / 上抬时长
    目标Pitch = 按上抬曲线插值(0, Pitch总幅度, 进度)
    目标Yaw   = 按上抬曲线插值(0, Yaw总幅度, 进度)
    本帧Pitch增量 = 目标Pitch - 上一帧Pitch目标值
    本帧Yaw增量   = 目标Yaw   - 上一帧Yaw目标值
    缓存当前目标值
    返回 本帧Pitch增量, 本帧Yaw增量
```

### 3.2 本项目的策划友好版（等价改写）

```
【每个固定步长步】分两件事：先推时间，再算输出。

一、推时间（含帧率保护，见第 4 节）
    固定步长 = 1/60 秒
    攒够一个固定步长，就执行一次「步进」：
        阶段内已过时间 += 固定步长
        如果 阶段内已过时间 > 当前阶段总时长:
            阶段内已过时间 = 当前阶段总时长      ← 跨界钳制，保证曲线跑满 100%

二、按当前阶段算输出（每一步都算，不跳步）

    阶段 t0 上抬：
        进度     = 阶段内已过时间 / 上抬时长
        目标Pitch = 上抬曲线插值(0, 本发Pitch幅度, 进度)
        目标Yaw   = 上抬曲线插值(0, 本发Yaw幅度,   进度)

    阶段 t1 回弹：
        进度     = 阶段内已过时间 / 回弹时长
        目标Pitch = 从上抬峰值 插值到 峰值×回弹比例
        目标Yaw   = 从上抬峰值 插值到 峰值×回弹比例

    阶段 t2 稳定：
        目标Pitch = 回弹终点值（不变）
        目标Yaw   = 回弹终点值（不变）

    阶段 t3 下降：
        进度     = 阶段内已过时间 / 下降时长
        目标Pitch = 从回弹终点值 插值到 峰值×残留比例
        目标Yaw   = 从回弹终点值 插值到 峰值×残留比例

三、转成相机能用的增量（这一步是灵魂）
    本步Pitch增量 = 目标Pitch - 上一步Pitch目标值
    本步Yaw增量   = 目标Yaw   - 上一步Yaw目标值
    相机补间输出 += 本步增量
    缓存当前目标值 = 目标Pitch / 目标Yaw

四、阶段推进
    如果 阶段内已过时间 >= 当前阶段总时长:
        切到下一阶段，阶段内已过时间 -= 当前阶段总时长
        （t3 结束后进入回正完成，走稳态残留）
```

> **为什么必须有第三步？**
> 因为相机每帧只能「转一点」，不能直接设绝对角度 —— 玩家自己也在动鼠标，绝对设值会把玩家输入冲掉。
> 所以算法内部始终维护一个「目标值」，每帧把「目标值的变化量」推给相机。这也是参考文档 §7 单列的一条要点。

## 4. 低帧率与帧率不稳的处理（本轮重点）

### 4.1 问题

单发阶段都很短（上抬常见 0.03~0.08 秒）。如果直接拿渲染帧的 `DeltaSeconds` 推进：

| 帧率 | 一帧时长 | 0.06 秒的上抬段 |
| --- | --- | --- |
| 144fps | 6.9ms | 采到 ~9 个点，形状完整 |
| 60fps | 16.7ms | 采到 ~4 个点，形状基本准确 |
| 30fps | 33.3ms | 采到 ~2 个点，**形状被抹平成直线** |
| 20fps | 50ms | 采到 ~1 个点，**终点都到不了** |

结果就是**同一把枪在不同机器上手感不同**，且帧率抖动时单发幅度会跟着抖。

### 4.2 三项处理

#### ① 固定子步长（核心）

`Advance(DeltaSeconds)` 内部不再直接把整帧时间喂给阶段计时，而是攒进一个累加器，**以 1/60 秒为单位循环推 N 次**：

```
累加器 += 本帧时间
执行次数 = 0
当 累加器 >= 1/60 秒 且 执行次数 < 子步上限:
    累加器 -= 1/60 秒
    执行一次步进（第 3.2 节的「一」「二」「三」「四」）
    执行次数 += 1
```

**效果**：无论显示器多少 Hz，这段曲线被采样的点密度恒定为 60Hz。20fps 和 144fps 跑出同一条轨迹。

#### ② 阶段终点跨界钳制（文档原文要求）

参考文档 §2 原话：

> 「由于单发后座过程很短，阶段结束时可能出现离散时间跨越边界的情况，例如某阶段目标时长为 0.06 s，而固定步长无法刚好命中该时刻。如果不处理，插值曲线可能无法完整跑到终点。常见处理方式是在即将跨越阶段终点时，将累计时间钳制到阶段终点，确保曲线能取到 100% 的终值。」

```
预计时间 = 当前时间 + 固定步长
如果 预计时间 会跨过当前阶段终点:
    当前时间 = 当前阶段终点
否则:
    当前时间 = 预计时间
```

**效果**：曲线一定跑到 100%，上抬幅度不会因帧率而缩水。

#### ③ 子步上限（防 spiral of death）

如果某一帧卡了 500ms，按 1/60 秒切分会得到 30 个子步 —— **本该卡一帧，结果推 30 次，卡得更久**。这是经典的死亡螺旋。

```
子步上限 = 8
```

超出的时间**直接丢弃**（不补给后续帧，避免误差累积）。丢弃时把当前阶段钳到终点，保证状态机不会停在半路。

> **为什么上限是 8 而不是更高？**
> 8 个子步 = 133ms，已经覆盖到 7.5fps。再低的帧率下玩家感知不到单发形状的细节，继续推只是白白拖慢恢复。宁可丢时间也不能进死亡螺旋。

### 4.3 为什么**不**额外做「补间后置平滑」

一个常见的补充方案是对 `CameraOffsetPitch/Yaw` 再叠一层指数平滑（`FInterpTo`），让帧率突变时输出不跳。

**本项目不做**，理由：

1. 固定子步长已经把「采样密度」这件事彻底解决了 —— 平滑只能掩盖抖动，不能修正轨迹。
2. 平滑会引入**必然的延迟**。后坐力是「手感」系统，镜头响应延迟比几毫秒的抖动更伤。
3. 多一个旋钮 = 多一处策划会配错的地方。**能用一个开关解决的，不加第二个。**

如果将来真出现观感问题，再加开关也不迟 —— 但先按「无延迟最优解」落地。

### 4.4 验收方式（自动化测试）

新增用例 `Lyra.Recoil.Interp.FrameRateInvariance`：

```
同一份 Interpolated 配置，分别用 3 种帧率推进相同的总时长：
    A: 1/20 秒步长（20fps）
    B: 1/60 秒步长（60fps）
    C: 1/144 秒步长（144fps）

断言：三者推进到相同时刻后，AccumulatedPitch 逐点相等（容差 1e-4）
```

这条用例**只有方案 ③ 能通过** —— 只做跨界钳制的话 B/C 的形状会和 A 不同，测试直接红。

### 6.1 分配

> **注意**：`ERecoilSingleShotMode` 的**结构默认值仍是 `InstantWrite`** —— 既有的 `DA_Recoil_Rifle`
> 与自动化测试使用的内存 Profile 都依赖它。场上两把枪的资产各自显式配成 `Interpolated`。

两把枪同属步枪族，切换开关就能直接对比两套模型 —— 这是「共存」的价值所在。

### 6.2 `LiftCurve` 默认形状：Ease-Out（先快后慢）

默认上抬曲线取 **Ease-Out**，即「开火瞬间抬得最快，随后逐渐减速到目标值」。

曲线关键帧（X = 段内进度, Y = 上抬完成度）：

| X | Y |
| --- | --- |
| 0.00 | 0.00 |
| 0.15 | 0.35 |
| 0.35 | 0.62 |
| 0.60 | 0.83 |
| 1.00 | 1.00 |

**为什么是 Ease-Out 而不是线性或 Ease-In？**

1. **物理直觉**：枪机后座是冲量驱动的 —— 加速度在开火那一瞬间最大，随后被复进簧和射手肩部吸收，速度递减。Ease-Out 最贴近这个物理过程。
2. **观感**：射击的「爆发感」来自**起始的快速位移**。线性曲线会让上抬显得拖沓；Ease-In（先慢后快）更糟，会让开火瞬间「没反应」，然后突然窜上去。
3. **包容低帧率**：Ease-Out 在前 1/3 段就完成了约 60% 的位移，即使只采到 2 个点（30fps 极端情况），保留下来的也是「主要位移」，而非「零位移」。
4. **行业惯例**：主流 FPS 的上抬处理普遍采用「起手快、收尾慢」的节奏 —— 它同时满足了「像有后坐力」和「不像被硬拽」两个诉求。线性在这两点上都吃亏。
5. **与回弹段配合**：Ease-Out 到顶后接 `ReboundRatio = 0.72` 的回弹，形成「窜上去 → 掉回来一点 → 稳一下 → 慢慢落回去」的节奏，这正是参考文档 §2 四段式想要的顿挫感。

`ReboundCurve` 默认取**线性** —— 回弹是个短促的「掉一下」，形状不敏感，线性最不容易配错。

## 7. 连发情境下的阶段重叠处理

高射速武器（`Rifle_S` 射速 < `LiftDuration + ReboundDuration + RecoveryDelay`）连发时，**上一发的时间轴还没走完，下一发就来了**。

处理规则（三条，按优先级）：

1. **新发直接重置阶段时间轴为 t0**，而不是排队 —— 排队会引入输入延迟，手感想都不敢想。
2. **逻辑偏移照常累加**（这一步和 `InstantWrite` 完全一致），所以峰值/回正/弹道链的语义不变。
3. **补间输出的连续性由「目标值差分」自动保证** —— 新发的目标值从「当前上抬段起点 = 当前逻辑偏移」开始算，所以补间输出会从当前值平滑地继续往上，**不会跳变**。

```
第 1 发:  ─╱‾╲___
第 2 发:      ─╱‾╲___          ← 第 2 发在 t1 回弹中途插入，直接重启 t0
              ↑
         逻辑偏移在此处是连续累加的，
         补间输出从「当前值」继续，无跳变
```

> **代价说明**：连发时每发都走不完完整的上抬-回弹，观感上更接近「持续被推高」而不是「一发一顿」。这是**正确**的行为 —— 射速快到一定程度，单发的顿挫感本来就应该被连发节奏吞掉，否则会显得粘滞。真想要明显的逐发顿挫，把 `LiftDuration` 调短。

## 10. 与参考文档 §2 的对照

| 文档要求 | 本文落地 | 位置 |
| --- | --- | --- |
| 单发射击拆为多个阶段 | 三段式（稳定段复用 `RecoveryDelay`） | §1 |
